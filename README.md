## 二、系统定位

中型研发团队的线上环境三年内就会从十几台服务器膨胀到上千个资源对象 —— 云主机、K8s 节点、中间件集群、数据库实例散落在七八套互不相通的控制台里。值班的人靠经验判断哪台机器快撑不住，巡检靠临时脚本、结果散在聊天记录里，告警先被重复通知淹没再花时间定位。

SmartOps 要做的不是「再多一个监控大屏」，而是把 **发现问题 → 判断问题 → 处理问题 → 复盘问题** 串成闭环。

### 五层架构

```
用户层      四类角色统一入口
应用层      七个功能模块（用户直接操作的部分）
支撑层      采集 / 调度 / 检测 / 归并 / 执行（公共能力，供应用层复用）
数据层      时序指标 / 关系数据 / 缓存 / 消息 / 文件
被管资源层  多云主机 / K8s / 中间件 / 数据库 / 网络设备
```

层间只通过明确定义的接口通信，下层不感知上层业务语义 —— 保证任意一层可以独立替换或横向扩展。

### 七个功能模块

| 模块 | 职责 |
|---|---|
| 资源纳管 | 异构资源统一接入，维护台账、分组标签与依赖拓扑 |
| 巡检编排 | 把巡检经验沉淀为模板与 DAG 流程，按计划批量执行 |
| 监控与异常检测 | 时序指标采集与可视化，多模型算法发现劣化趋势 |
| 告警中心 | 规则产生告警，聚合抑制、分级派单、跟踪闭环 |
| 自愈与工单 | 自动处置高频故障，失败转单并跟踪 SLA |
| 报表中心 | 自动汇总巡检与告警，产出可交付报告 |
| 系统管理 | 多租户隔离、角色权限矩阵、审计留痕 |

## 三、非功能指标（写进设计里的量化约束）

设计文档最容易含糊过去的就是非功能需求。这份文档给了具体数字：

| 类别 | 指标 |
|---|---|
| 性能 | 纳管 5000 个资源对象；单次千节点巡检 5 分钟内完成；指标写入吞吐 ≥ 5 万点/秒；告警产生到通知送达 ≤ 3 秒 |
| 可靠性 | 采集通道中断自动降级为轮询、不丢指标；告警降噪保留原始记录、可追溯；核心服务无单点 |
| 安全性 | 凭据由凭据库加密托管，不落库不传输明文；高危动作（删除资源、执行自愈）二次确认；审计日志不可篡改 |
| 易用性 | 接入一个资源 ≤ 4 步向导；告警处理主路径 ≤ 2 次点击 |
| 可扩展性 | 采集插件、检测算法、通知渠道、自愈动作均插件化注册，不改核心服务即可扩展 |

## 四、界面原型怎么做的

28 张界面原型没有一张是手工画的，走的是「设计令牌 → HTML 组件 → 无头浏览器渲染截图」的流水线：

```
① AI 定义 Design Token（色值 / 圆角 / 间距 / 字号阶梯 / 状态色）
        ↓
② 生成共享样式表 + 页面外壳（侧边导航 + 顶部工具条 + 内容插槽）
        ↓
③ 逐页生成内容片段，构建脚本拼装外壳与片段
        ↓
④ 无头 Chrome 在 1440 宽、2 倍像素密度渲染截图
        ↓
⑤ 人工复核 → 溢出 / 折行 / 层级不清 → 回到片段定点修正 → 重新渲染
```

为什么这么做，而不是用图形软件逐张画：

- **十余张界面视觉完全一致** —— 它们共享同一套设计令牌，不是靠手感对齐
- **原型本身是可运行的前端结构**，后续开发可直接复用
- **可复现、可微调** —— 改一个令牌，全部页面同时生效

第 ⑤ 步不能省。渲染出来才能发现的问题，光看代码是发现不了的 —— 比如表格内容溢出、长文案折行后挤压行高、深浅背景下状态色对比度不足。

### 设计令牌的关键约束

状态色必须同时提供 **色值 + 低透明度底色 + 同名描边** 三件套。只给色值的话，同一套状态色放在深色面板和浅色表格里必然有一处读不清。

## 六、这份文档的边界

- **只有设计，没有实现代码。** 数据结构与接口定义到字段与方法签名一级，但服务端、采集端均未编码。
- 非功能指标是**设计目标**，不是压测结论 —— 没有实现就不可能有实测值。
- 界面原型是 HTML 渲染件，描述了信息架构与交互形态，但不含业务逻辑。
- 演示数据为构造的运维场景样例（主机名、IP、指标值），非真实环境数据。
